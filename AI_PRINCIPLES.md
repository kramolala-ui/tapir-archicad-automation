# AI Principles — работа с форком Tapir-архикад-автоматизации

**Назначение.** Этот файл — стартовый контекст для LLM, которая
начинает работу над нашим форком Tapir-аддона. Прочитай его целиком
до того, как предлагать правки. Он короче и честнее, чем README,
и описывает реальное положение вещей, а не желаемое.

**Аудитория.** LLM через AI Bridge (`===AI_REQUEST===`,
`===AI_CHANGES===`), пишущая код в ветку `fresh`.

---

## 1. Что это за проект

Форк [ENZYME-APD/tapir-archicad-automation](https://github.com/ENZYME-APD/tapir-archicad-automation)
от `kramolala-ui`.

- **Upstream** — 105 команд, JSON API к Archicad через Graphisoft add-on
  механизм (`ACAPI_AddOnAddOnCommunication_InstallAddOnCommandHandler`).
- **Наш форк** — 260 команд: добавлены MEP, IFC, слои, аннотации,
  solid operations, **rotate elements**, копирование/поворот, операции
  с зонами, ключевые ноты, скрипт-UI.
- **Зачем форк:** upstream не двигается (последний релиз давно, автор
  занят), а нам нужны команды, которых там нет, и оптимизации, на
  которые upstream не пойдёт.

**Где живёт истина:** рабочая ветка в GitHub — **`fresh`**. Это не
`work` (там upstream + 1 наша команда), не `main` (upstream), не
`cpp_bridge/work`. Все правки аддона — только в `fresh`.

**Локальная копия:** `C:\Python_projects\tapir-custom\archicad-addon\`
на машине разработчика. Она может быть свежее или старше `fresh` —
перед работой всегда уточняй у пользователя, куда писать: если
через AI Bridge → `@fresh`; если через локальный AI_PROGRAM →
`tapir-custom`.

## 2. Workflow правок

```
LLM (AI Bridge, @fresh)
  → правки в GitHub-ветку fresh
  → пользователь собирает аддон через GitHub Actions
  → скачивает .apx (Win) / .bundle (Mac)
  → устанавливает в Archicad
  → тестирует живой проект
  → синхронизирует с локальным tapir-custom (иногда)
```

**Правила правок:**

1. Всегда проверяй, что путь в `@fresh`, а не `@work` / `@main`.
2. До правки — `stat` или `read`, чтобы убедиться, что файл не
   изменился с прошлой сессии.
3. Новый `.hpp/.cpp` в `Sources/` подхватывается CMake-глобом
   автоматически. Не нужно править `CMakeLists.txt` — он тривиален
   и делегирует всё в `Tools/CMakeCommon.cmake`.
4. Регистрация команды — всегда в `AddOnMain.cpp::Initialize`.
   Место вставки: **до** блока «Loading the palette singleton…». Это
   критично — если палитра упадёт, все команды, объявленные после
   неё, не зарегистрируются (баг #516, уже отловлен на живом).
5. Один блок `AI_CHANGES` = 3-5 правок максимум. `write` большого
   файла — отдельным блоком.

## 3. Архитектура аддона

### CommandBase

Базовый класс — `Sources/CommandBase.hpp`. Наследники реализуют:

- `GetName()` — имя команды как видит клиент (без namespace).
- `GetInputParametersSchema()` — JSON-схема входных параметров.
- `GetResponseSchema()` — JSON-схема ответа.
- `Execute(params, processControl)` — сама работа.
- `GetNamespace()` — `final` в базовом, всегда `TapirCommand`.

**Важно:** `namespace` и `execution policy` — `final`. Их нельзя
переопределить. Это значит: всё, что делает наш аддон, — это
стандартные API-команды Archicad. Никаких своих HTTP-серверов, никаких
своих endpoint'ов. Транспорт полностью закрыт Graphisoft'ом.

### Поток данных

```
Python-клиент → JSON → Graphisoft runtime → GS::ObjectState
                  → CommandBase::Execute(params) → ответ ObjectState
                  → Graphisoft runtime → JSON → Python
```

**Пункт «Graphisoft runtime парсит JSON в ObjectState» — самый
медленный.** Он не наш, мы не можем его заменить. Единственный способ
обойти — упаковать данные в **одну строку** (`payload_b64`) и
парсить её самим внутри `Execute`.

### Группы команд

`CommandGroup` — чисто организационная сущность. Создаётся в
`Initialize`, в неё через `RegisterCommand<Cmd>(group, version, description)`
складываются команды. Порядок — не важен, но по стилю идут группами:
Application, Project, Element, Element Creation, Attribute, Property,
Classification, IFC, MEP, SolidElementOperation, ScriptUI, Developer.

## 4. Что делаем сейчас: bulk-транспорт

### Проблема

Массовые операции (3000 свойств × 20000 объектов) упираются в:

1. **Graphisoft JSON-парсер** — сходит с ума на больших JSON.
2. **Лимит батча ~500 элементов** — приходится делать 40 HTTP-раундов.
3. **Ручной `ACAPI_Element_GetPropertyValuesByGuid`** в цикле по
   одному элементу — 500 вызовов ACAPI там, где нужен один пакетный.

### Решение: base64(msgpack(zstd(data)))

Не меняем транспорт Graphisoft. Оборачиваем тяжёлые данные в одну
JSON-строку `payload_b64`:

```
Python:
  data → msgpack → zstd → base64 → "payload_b64": "..."

C++ (в Execute):
  payload_b64 → base64-decode → zstd-decompress
              → msgpack-parse → обработка порциями ВНУТРИ одного вызова
```

**Что это даёт:**

- Один HTTP-запрос вместо 40.
- Парсинг внутри аддона — на своей стороне, без схемы, быстро.
- Сжатие zstd — 5-10× по объёму для JSON-подобных данных.
- base64 съедает 33%, но это в разы меньше, чем выигрыш.

### Порядок внедрения

| # | Шаг | Статус |
|---|---|---|
| 1 | `BulkPing` — base64 only, проверить транспорт | **сделано** |
| 2 | Подключить zstd через FetchContent | TODO |
| 3 | Подключить msgpack-cxx (header-only) | TODO |
| 4 | `Bulk.GetPropertyValues` на существующем ACAPI | TODO |
| 5 | Пакетный ACAPI в `PropertyCommands.cpp` | TODO |
| 6 | Остальные bulk-команды (set, gdl, details) | TODO |

**Не начинать шаг N+1, пока не проверен на живом шаг N.** Одна
команда за раз — так проще откатить, если что-то пойдёт не так.

## 5. Известные грабли

### AC26: `CreateObjects` падает с `-2130313112`

`ACAPI_Element_Create` не создаёт Object на Archicad 26 в некоторых
конфигурациях. Симптом: `{"error": {"code": -2130313112, "message":
"Failed to create new Object"}}`. При этом полилинии, плиты, колонны
через тот же аддон создаются нормально — проблема именно с library parts.

**Обход:** `RotateElementsByAngle` с `withCopy: true` + `ModifyObjects`
для сдвига/поворота копии. Это работает и проверено на живом.

### `ModifyObjects` не устанавливает `dimensions.x` напрямую

При `useFixSize: true` (а он по умолчанию `true` у библиотечных
объектов) параметр `dimensions.x` в `ModifyObjects` игнорируется
молча. Надо явно передавать `useFixSize: false` в том же вызове.

**Важно:** после этого длина управляется через **`MEP_StraightLength`**
(GDL-параметр), а не через `A` напрямую. `A` — производный и
пересчитывается сам после установки `MEP_StraightLength`.

### GDL-параметры могут пересчитываться асинхронно

`SetGDLParametersOfElements` возвращает `success: true` сразу, но
значение читается старым ещё несколько сотен миллисекунд. Если надо
проверить — подождать `time.sleep(0.3-0.5)` или перечитать дважды.

### `EntityType.BIM` не существует

В Python-коде (в IFC Explorer) правильный тип для Object —
`EntityType.BIM_OBJECT`. Ошибка `AttributeError: type object 'EntityType'
has no attribute 'BIM'` — признак, что использовано короткое имя.

### `archicad_get_elements` не пишет `libPart` в параметры

Возвращает `element_type`, `bbox_*`, `ArchicadDetail/origin.*`,
`story_index`, но **не** `ArchicadDetail/libPart.name`. Чтобы
определить библиотечный элемент, надо отдельно звать
`GetDetailsOfElements` и смотреть в `details.libPart.name`.

### Палитра загружается последней

`TapirPalette::Instance()` в конце `Initialize` — обёрнута в
`try/catch`. Если упадёт, команды, зарегистрированные **до** неё,
работают; команды **после** — нет. Всегда добавляй новые команды
**до** этого блока.

## 6. Стиль кода

- **C++17** (AC26-28), **C++20** (AC29+). Не используй более
  свежие фичи без необходимости.
- **Отступ — 4 пробела**, стиль GS/Graphisoft (см. любой `*.cpp`
  в `Sources/`).
- **Пробел перед скобкой вызова:** `Foo (args)`, `if (x)`, `for (...)`. Это соглашение Graphisoft, не наш каприз.
- **`GS::ObjectState`** для входов/выходов — везде. `std::unordered_map`
  внутри, если нужен быстрый доступ.
- **Namespace** — `TapirCommand`, единый для всех наших команд.
  Отдельные namespace не заводить.
- **Логирование** — `ACAPI_WriteReport(...)` для важных событий,
  `DBPrintf` для отладочных.
- **Undoable command**: если команда меняет модель — оборачивай в
  `ACAPI_CallUndoableCommand("CommandName", [&]() { ... })`.
- **Комментарии** — по-русски в новых файлах, по-английски если
  файл создаётся с нуля под upstream-стиль. Язык не критичен, важнее
  смысл.

## 8. Границы

### Что можно

- Добавлять новые команды.
- Переписывать внутренности существующих команд, если это не
  меняет их JSON-схему входа/выхода.
- Добавлять опциональные параметры с дефолтами (backward compatible).
- Оптимизировать ACAPI-вызовы внутри существующих команд.

### Что нельзя

- Менять namespace команды (`TapirCommand` — `final`).
- Ломать JSON-схему существующих команд (клиенты сломаются).
- Удалять команды без явного запроса пользователя.
- Пытаться сделать свой HTTP-сервер / endpoint — невозможно через
  API-команды.
- Пушить в `main` или `work` — только `fresh` (или рабочая ветка
  текущей задачи).

### Что пока под вопросом

- Возвращать ли изменения в upstream. Решено отложить: сначала
  пусть bulk-протокол докажет себя в работе в течение 1-2 месяцев,
  потом решим про PR.
- Мержить ли `fresh` и `work`. Пока нет — `work` служит каналом
  для экспериментов с upstream-совместимостью.

## 10. История решений

**2026-10-05:** Решено делать base64+msgpack+zstd в форке, а не
ждать upstream. Причины: (1) upstream не двигается; (2) наш форк
уже сильно впереди; (3) «честность» здесь = правильно указать
fork в README и не жаловаться в upstream issues, а не отдавать
всё туда немедленно.

**2026-10-05:** Решено вендорить msgpack-cxx и zstd в репо, а не
требовать у пользователя vcpkg/brew. Причина: аддон должен
собираться «из коробки» без внешних менеджеров пакетов.

**2026-10-05:** Написан `BulkPing` (шаг 1). Транспорт base64
Python → C++ работает. Дальше — zstd, потом msgpack.
